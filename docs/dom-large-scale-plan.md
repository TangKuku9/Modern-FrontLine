# Dom 占点模式大规模化计划（30v30 / 50v50）

> 状态：**执行中**（2026-10-09 立项）。本文是 Dom 模式扩展到 30v30 / 50v50 的
> 可行性结论与分阶段实施计划。性能为主线，游戏性为次要线。
> 上游依据：`net-server-performance-audit.md`（实测基线）、
> `net-performance-audit-round3.md` W2（协议天花板立账）、`net-bug-list.md`
> （"MAX_SEATS=16 是性能悬崖不是设计"的预警）。

## 0. 结论

**CPU 不是瓶颈，带宽模型才是。**

- 服务器单房 tick 预算 16.7ms，16 人房实测 0.09–0.16ms/拍，`room.step` 整体
  O(N)，外推 100 实体约 1.5–2.5ms/拍（ridges 大图口径），余量 >80%。
- 快照是 20Hz 全量广播（无 AOI、无 delta）：每客户端 `(12 + 26×N)B × 20Hz`。
  - 30v30（60 实体）= 251 kbps/人，服务器出口 ~15 Mbps/房 —— 可接受但不优雅；
  - 50v50（100 实体）= 418 kbps/人，出口 ~42 Mbps/房 —— 弱网不可用，必须先动协议。
- 挡在门口的不是 `MAX_CLIENTS=128` 或协议量程（count u16、id u16、
  snapScratch 128 实体都够用），而是 `MAX_SEATS=16` 背后的性能悬崖：
  记分板 O(N²) 每 2s、全量快照 O(N²)、100 个非实例化 Soldier 客户端模型。

**分阶段判定：30v30 = 中小改造（阶段 0+1）；50v50 = 必须动协议红线（阶段 2）。**

## 1. 用户边界目标（SLO）

| 边界 | 现状判据 | 大规模目标 |
|---|---|---|
| 服务器 tick | hz≥57（soak 判据） | p95 hz≥59；单房 stepMs p99 ≤8ms（预算 16.7ms） |
| 快照到达率 | 每人下行 ≥15Hz | p95 ≥18/20Hz；弱网（3% 丢包）≥14Hz |
| 端到端手感 | 插值延迟 100ms + 服务器回溯窗 1s | 不变（与人数无关，O(1)/玩家） |
| 客户端帧率 | 未定义 | p95 ≥50 FPS @60 实体 / ≥45 FPS @100 实体（中端 GPU） |
| 服务器出口 | 无 | ≤8 Mbps/房（60 实体，阶段 1 后）；≤10 Mbps/房（100 实体，阶段 2 后） |

## 2. 压测方法论

`soak.mjs` 阶梯从 16/房 扩到单房 60 实体，全部跑 ridges（dom 专属 360m 图）：

- **阶梯负载**：单房 [20, 40, 60] 假客户端（60Hz 输入 + ack）。
- **峰值交火**：60% 实体集中于单旗 30m 圈内（dom 真实分布，事件密度最高）。
- **Soak**：60 实体单房 ≥30 分钟，观察 GC、`pose` 环、噪声表压实稳态。
- **停止判据（拐点记录）**：hz<57 / behindMs>150 / 单连接 bufferedAmount 持续
  >128KB / 快照到达 <14Hz —— 命中即记为实测拐点。
- **验收链**：`gate.mjs` 确定性闸 + `test/net-audit.mjs` fanout 纪律判据
  （协议改动红线回归线）+ `test/room-bots.mjs`。

## 3. 饱和信号（USE）

| 资源 | 信号 | 60 实体 | 100 实体 |
|---|---|---|---|
| 服务器 CPU | /healthz stepMs / hz / behindMs | ~1ms/拍 | ~1.5–2.5ms/拍 |
| 出口带宽 | 每房聚合 Mbps | 15（改前）→ 6–8（阶段1后） | 42（改前）→ 6–10（阶段2后） |
| 客户端下行 | kbps/人 | 251 → ~100–130 | 418 → ~60–100 |
| WS 发送缓冲 | bufferedAmount（闸 256KB） | 安全 | 弱网 2.5s 可触顶 → 需年龄指标 |
| 客户端 GPU | FPS / draw call | 60 模型可控 | 100 模型需 LOD（阶段1）/ Impostor（阶段2） |

## 4. 热点清单（按严重度）

| # | 热点 | 复杂度 | 处理 |
|---|---|---|---|
| 1 | 快照全量广播（无 AOI 无 delta） | O(N²) 字节 | 阶段1 AOI + 花名册；阶段2 delta |
| 2 | board 记分板全量扇出每 2s（room.mjs） | O(N²) | **阶段0** Top-N 裁剪 |
| 3 | 客户端 100 个 Soldier 逐兵逐帧动画 | O(N×帧) | **阶段1** 动画频率 LOD |
| 4 | 服务端 Bot 完整骨骼动画+IK（~12% 拍内） | O(bots) | **阶段1** 降频/下线重审 |
| 5 | Bot perceive 全表扫 @6Hz + A* 预算 3/tick | O(bots×N) | 现有预算封顶，暂不动 |
| 6 | flagsTick / pose.record / fillEnemies | O(N)/拍 | 已零分配，不动 |
| 7 | TCP 队头阻塞 | 架构 | 阶段2 WebTransport 立项 |
| 8 | welcome 开局扇出 O(N²) 一次性 | ~400KB 突发 | round3 已判不值得动，维持 |

## 5. 实施阶段

### 阶段 0 —— 解除硬上限 + 取证（30v30 试跑门槛）

1. `MAX_SEATS 16→64`、`MAX_PER_TEAM 8→32`（lobby.mjs）；
   `maxClients 128→200`（net-server.mjs CFG 默认值）。snapScratch 128 实体不动。
2. **board Top-N 裁剪**：事件只带 Top 16 行 + 自己一行 + 双方队伍合计；
   榜单展开走请求-响应（不推全量）。HUD 按 `more` 标志提示可展开。
3. soak 阶梯扩到单房 60 实体并跑通，记录实测 stepMs / hz / 带宽（更新本文 §7）。
4. 回归：net-audit、room-bots、gate 全绿。

**验收**：单房 60 实体 hz≥59、behind<150ms；100 人对局可开（不保证弱网体验）。

### 阶段 1 —— 30v30 正式支撑（协议小动：AOI + 花名册）

1. **距离 AOI（200m）**：快照按客户端裁实体表（编码一次→按人编码）。
   快照字段与实体顺序**不动**（26B/实体布局保持，count 按人计算）。
2. **花名册事件**：新事件 `roster`，分片携带全房名单（cid/team/name/bot/alive）；
   周期 2s 全量一班；实体进出 AOI 时即时增量。客户端据此区分
   "离开视野"与"离开游戏"，全房记分板/小地图数据源不变。
3. **客户端动画频率 LOD**：30m 外 15Hz、80m 外 5Hz（姿态插值照常平滑）。
4. **服务端 Bot 骨骼动画降频**（快照只吃姿态，不吃骨骼视觉）：动画更新降到
   1/4 拍频（15Hz），不改语义。
5. 回归 + soak 复测，记录带宽前后对比（更新本文 §7）。

**红线纪律**（照抄第一轮协议线）：版本化协议号、旧客户端拒绝入 AOI 房的兼容
策略、gate.mjs 确定性对照、net-audit 判据随协议同步更新。

**验收**：60 实体每客户端下行 ≤130 kbps、出口 ≤8 Mbps；快照到达率与现在
16 人房无显著差异；net-audit / room-bots / gate 全绿。

> **落地记录（2026-10-09，阶段 0+1 已完成）**——两处与上面计划的偏差，均为实现时收敛：
> 1. 第 2 条"花名册事件 roster"没有做独立事件：客户端 `proto:2` + 快照缺席
>    grace（15 份 ≈0.75s，期间 setFar 隐藏、超时才 beginLeave）已能区分"走出
>    200m"与"退房/掉线"，全房名单走 board Top-N 定向事件（BOARD_MAX_ROWS=16）。
>    少一条周期事件流，等真机出现"需要全房实时花名册"的需求再立账。
> 2. 第 4 条 Bot 动画降频 1/4 落成**headless 直接跳过**（js/ai.js 以 `game.headless`
>    门住骨骼/根变换/脚步声/枪口火光，保留 phase/crouchT/flashT/slideT/sprinting
>    等快照消费字段）——服务端本来就没有可渲染的画布，动画计算全是白工，跳过
>    优于降频。gate.mjs 确定性四项全绿（视觉字段不在 sim 语义内）。
> 实测数字见 §7。

### 阶段 2 —— 50v50（协议红线动工，**未立项，仅立账**）

1. 增量编码（delta 省 50–80%；W2 立账项，含版本化协议 + 兼容策略）。
2. 频率分层：近距 20Hz / 远距 5Hz。
3. WebTransport 不可靠通道立项，WebSocket 回退。
4. 客户端远距 Impostor，活跃 Soldier 模型压到 ~25。
5. 游戏性配套：5 点制（A–E）、占点力封顶 `DOM_MAX_FORCE_PER_FLAG`、
   波次复活分批错峰、计分目标回调。

## 6. 过载与背压（运行期护栏）

- 背压闸 256KB 只跳快照不跳事件（优先级正确：命中确认 > 状态更新），保留。
- 补充：快照饱和先降频（20→10Hz）再丢弃；`bufferedAmount` 增加"最老未发字节
  年龄"指标（>1s 视为该客户端网络饱和），把静默丢弃变可观测。
- 入口限流（240 msg/s/连接、6 连接/IP、2 房/账号）不动。

## 7. 实测记录（2026-10-09 回填，本机 win11 / Node 22）

> 命令：`node server/soak.mjs --ladder=1 --per=N --map=yard|ridges --proto=1|2`
> （soak 已带 `--per/--proto/--map` 与下行 kbps 列；快照 20Hz/人，26B/实体。）

| 场景 | 图 | 实体 | hz | stepMs | 每人下行 | 出口 | 判定 |
|---|---|---|---|---|---|---|---|
| 基线（改造前） | yard | 16 | 60.6 | 0.16 | 68 kbps | 1.1 Mbps | 绿 |
| 阶段0 r20 | yard | 21 | 60.6 | 0.16 | 92 kbps | 1.85 Mbps | 绿 |
| 阶段0 r40 | yard | 41 | 59.5 | 0.23 | 176 kbps | 7.04 Mbps | 绿（贴 SLO） |
| 阶段0 r60 | yard | 61 | 59.5 | 0.31 | 260 kbps | 15.6 Mbps | CPU 绿 / 带宽红 |
| 阶段1 r60 全量（proto1） | ridges | 61 | 60.3 | 0.29 | 260 kbps | 15.6 Mbps | 对照基线 |
| **阶段1 r60 AOI（proto2）** | ridges | 61 | 59.9 | 0.42 | **173 kbps（-33%）** | **10.4 Mbps** | 带宽显著回落，仍超 8 Mbps SLO |

**阶段 0 结论**：CPU 从头到尾不是瓶颈——61 实体单房 59.5Hz、每拍 0.31ms、落后
0ms、堆 22MB。挡门的是带宽模型：yard/ridges 上全量快照 60 人 = 260 kbps/人、
出口 15.6 Mbps，超出 ≤8 Mbps/房 的 SLO 一倍，30v30 没有 AOI 不能开。

**阶段 1 结论**：AOI 在 360m 的 ridges 上把每客户端下行砍掉 1/3（260→173
kbps），hz 与落后不受影响；per-client 编码代价 0.13ms/拍（0.29→0.42）。两条
"没有额外开销/不降帧率"的边界也取证了：
- ≤24 实体（AOI_MIN_ENTITIES 以下）走共享缓冲，逐字节等于全量（yard r20：92=92）；
- 小图（yard，~120m，200m 圈罩全场）AOI 裁不掉实体（yard r40：176=176）——
  增益只在 ridges（两队营地隔 >200m）这类大图出现。

**对验收线的诚实记账**：173 kbps 未达"≤130 kbps/人"的目标线。原因：soak 假
客户端全部挤在出生点，同队 30 人恒在 + 营地边缘敌人在圈内，这是**最坏分布**；
真实对局玩家沿三线推进后分布会显著稀疏。出口 10.4 Mbps 同理。若真机实测仍超，
收敛路径在阶段 2（增量编码 + 频率分层），本轮不追加。

## 8. 风险

1. 阶段 0 前所有容量数字是外推——先测拐点再谈后续（本文 §7 回填后收敛）。
2. AOI 后"按包长反推实体数"的判据（room-bots / net-audit 部分）需随协议 v2 更新。
3. 100 人下"回溯命中他人"频率上升，误伤体感投诉会增加——规则问题，提前定调。
4. 增量编码的 RNG 流对齐是阶段 2 最大工程风险（gate.mjs 是唯一护栏）。
